5. PAYMENT PROCESSING (BACKEND) FLOW
================================================================================

  5.1 PAYMENT SESSION CREATION (createPaymentSession.js):
  --------------------------------------------------------
  Cloud Function: createPaymentSession (HTTP, us-central1)
  VPC Connector: icici-connector (ALL_TRAFFIC)
       |
       v
  Validate: amount, userId, paymentMode, tenantId, appId
       |
       v
  Generate Secure Transaction ID:
    Format: "RB{last8_of_timestamp}{random_hex}" (max 20 chars)
    Example: "RB12345678ABCD1234"
       |
       v
  Create Firestore document: payments/{txnId}
    Fields: uid, userId, tenantId, appId, amount, paymentMode,
            planName, status="PENDING", email, mobile, 
            isYearly, isSixMonths, limits, feature flags,
            createdAt, updatedAt
       |
       v
  Call ICICI Service:
    ├─ UPI:  iciciService.generateUpiQr({txnId, amount, email})
    └─ CARD/NET: iciciService.initiateSale({txnId, amount, email, paymentMode, ...})
       |
       v
  Update payments/{txnId} with redirectUrl or upiQR
       |
       v
  Return to Flutter: {success, txnId, paymentMode, redirectUrl, upiQR}


  5.2 PAYMENT CALLBACK (paymentCallback — ICICI Webhook):
  ---------------------------------------------------------
  ICICI Bank calls: paymentCallback endpoint after payment
       |
       v
  Extract transaction result from ICICI response
       |
       v
  Update payments/{txnId}:
    - status → "SUCCESS" or "FAILED"
    - paymentId, bankRRN, etc.
    - updatedAt
       |
       v
  This triggers processPaymentSuccess (Firestore document write trigger)


  5.3 PAYMENT SUCCESS PROCESSING (processPaymentSuccess):
  --------------------------------------------------------
  Trigger: onDocumentWritten("payments/{txnId}") — status transitions to SUCCESS
       |
       v
  Validate UID (skip if PENDING_ placeholder)
       |
       v
  Fetch user email from:
    1. {tenantId}/data/users/{uid}
    2. Fallback: Firebase Auth
       |
       v
  Calculate GST (18%) breakdown
       |
       v
  Generate Professional PDF Invoice (PDFKit):
    - Invoice number: INV-YYYYMMDD-XXXXXX
    - Company: Rooks & Brooks Technologies Pvt. Ltd.
    - GSTIN: 33AAMCR8640J1ZZ
    - Itemized breakdown with GST
    - Digital signature section
       |
       v
  Build branded HTML email with payment summary
       |
       v
  Write to Firestore 'mail' collection (triggers email sending)
       |
       v
  Update subscription record: {tenantId}/{tenantId}/subscription/{uid}
    - status: "active"
    - planName, isYearly, isSixMonths, price
    - startedAt, expiresAt (calculated)
    - remindersSent flags reset
    - Feature flags (limits, geoLocation, attendance, barcode, reportExport)


  5.4 PAYMENT ACTIVITY LOGGING (logPaymentActivity):
  ---------------------------------------------------
  Trigger: onDocumentWritten("payments/{txnId}") — any write after PENDING
       |
       v
  Mirror to: {tenantId}/{appId}/payment_logs/{txnId}
    - Only for SUCCESS or FAILED (skips PENDING to avoid premature collection creation)


  5.5 PAYMENT RECONCILIATION (reconcileStuckPayments):
  -----------------------------------------------------
  Schedule: Hourly (0 * * * *)
       |
       v
  Query: payments WHERE status="PENDING" AND createdAt <= 30min ago
       |
       v
  For each stuck payment:
    → iciciService.statusCheck(txnId)
    → Update to SUCCESS or FAILED based on bank response
    → Triggers processPaymentSuccess if SUCCESS

================================================================================

  6.1 INVOICE GENERATION (Flutter Side - InvoicePdfService):
  -----------------------------------------------------------
  InvoicePdfService.generateInvoicePdf()
    → PDF with: Invoice Number, Transaction ID, Customer Details
    → Plan name, Duration, Amount, GST breakdown
    → Company branding

  6.2 INVOICE EMAIL (InvoiceEmailService):
  ------------------------------------------
  processAndSendInvoice()
    → Check payment_logs/{logDocId} for invoiceSent status
    → Generate PDF via InvoicePdfService
    → Base64 encode PDF
    → Write to 'mail' collection with PDF attachment
    → Update invoice status: Pending → Processing → Sent

  6.3 RECEIPT GENERATION (ReceiptService):
  ------------------------------------------
  ReceiptService.generateReceipt()
    → Generates downloadable PDF receipt
    → Includes GST breakdown (18%: CGST 9% + SGST 9%)
    → Customer details, plan info, payment method
    → Saved to device temp directory

  6.4 EMAIL SENDING (Cloud Function: processMailDocument):
  ---------------------------------------------------------
  Trigger: onDocumentWritten("mail/{docId}")
    → SMTP via Nodemailer (Hostinger SMTP)
    → Supports attachments (PDF invoices)
    → Retry logic: 3 attempts with exponential backoff
    → States: PENDING → SENT | RETRY → ERROR

  6.5 EMAIL RETRY (scheduledEmailRetry):
  ----------------------------------------
  Schedule: Every 30 minutes
    → Query 'mail' collection WHERE status.state = "RETRY"
    → Reset to PENDING if nextRetryAt has passed

7. SUBSCRIPTION LIFECYCLE MANAGEMENT
================================================================================

  7.1 SUBSCRIPTION DATA MODEL:
  -----------------------------
  Path: {tenantId}/{tenantId}/subscription/{uid}
  Fields:
    - status: "active" | "expired"
    - planName, isYearly, isSixMonths, price
    - startedAt, expiresAt, nextBillingAt
    - updatedAt
    - limits: {engineers, customers, tickets, brands}
    - Feature flags: geoLocation, attendance, barcode, reportExport
    - remindersSent: {twoDay, oneDay}

  7.2 REAL-TIME MONITORING (SubscriptionExpiryService):
  ------------------------------------------------------
  Listens to: {tenantId}/{tenantId}/subscription (real-time stream)
       |
       v
  On each snapshot:
    → Extract expiresAt / nextBillingAt
    → Compare with current UTC time
       |
       ├─ [NOT EXPIRED]:
       |    → If status was 'expired' but date is valid → Auto-activate
       |    → If within 48 hours of expiry → Show notification
       |
       └─ [EXPIRED]:
            → Check for queued plan (SubscriptionQueueService)
            → If queued plan exists → Activate it automatically
            → If no queued plan:
               → Update Firestore status to 'expired'
               → Deactivate user
               → Redirect to PlanExpiredScreen

  7.3 SUBSCRIPTION STATUS CHECK (FirestoreService):
  ---------------------------------------------------
  isTenantActive(tenantId, appId):
    → Query subscription collection for status='active'
    → Validate expiresAt is future
    → Auto-expire if date has passed

  hasActiveSubscription(uid, tenantId):
    → Check specific user's subscription doc
    → Auto-expire and deactivate if date passed

15. FIRESTORE DATA MODEL & TENANT ISOLATION
================================================================================

  GLOBAL COLLECTIONS:
  ├─ global_user_directory/{uid}     → tenantId, appName, role, updatedAt
  ├─ payments/{txnId}                → Payment transaction records
  ├─ payment_logs/{logDocId}         → Centralized payment audit logs
  ├─ mail/{autoId}                   → Email queue (triggers SMTP sending)
  └─ otps/{email}                    → OTP codes for password reset

  TENANT-SCOPED STRUCTURE:
  {tenantId}/
  ├─ data/                           (Document: primary app data bucket)
  │   ├─ users/{uid}                 → User profiles (name, email, role, active)
  │   ├─ admin/{name}                → Legacy admin records
  │   ├─ EngineerLogin/{docId}       → Engineer credentials & online status
  │   ├─ Admin_details/{bookingId}   → Service tickets
  │   ├─ branding/config             → App branding (colors, logo, fonts)
  │   ├─ referral_codes/{code}       → Referral codes for sub-user registration
  │   ├─ payment_logs/{txnId}        → Tenant-specific payment audit trail
  │   ├─ payment_transactions/{txnId}→ Triggers receipt generation
  │   ├─ notifications/{autoId}      → In-app notification records
  │   └─ notifications_tokens/       → FCM tokens by role
  │       ├─ admin/tokens/{userId}
  │       ├─ engineer/tokens/{userId}
  │       └─ customer/tokens/{userId}
  │
  └─ {tenantId}/                     (Document: subscription bucket)
      ├─ subscription/{uid}          → Active subscription records
      └─ queued_subscriptions/{uid}  → Queued plan upgrades

  KEY DESIGN DECISIONS:
  - Subscriptions use tenantId as both collection AND document ID
    to prevent duplication between 'data' and named buckets
  - Feature flags (geoLocation, attendance, barcode, reportExport) stored
    on subscription doc, checked at runtime for feature gating
  - Plan limits (engineers, customers, tickets, brands) enforced per-tenant
