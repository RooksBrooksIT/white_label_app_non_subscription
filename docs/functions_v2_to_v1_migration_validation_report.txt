5. HANDLER AND EVENT COMPATIBILITY
================================================================================
Detailed evaluation of handler parameter transformations:

A. Firestore Triggers:
- Wildcard Access: In v2, wildcards were accessed via `event.params.tenantId`.
  In v1, they are accessed via `context.params.tenantId`. All 5 Firestore triggers
  have been updated to use `context.params`. [Confirmed by source inspection]
- Snapshots:
  * `onCreate`: Uses `snap.data()`.
  * `onUpdate`: Uses `change.before.data()` and `change.after.data()`.
  * `onWrite`: Uses `change.after.exists ? change.after.data() : null` to safely
    handle document deletions without throwing runtime exceptions.
- Reference Updates: Uses `change.after.ref.update(...)` instead of
  `event.data.after.ref.update(...)`.

B. Callable Functions (`adminProcessRefund`):
- In v2, `onCall` received `request` with `request.auth` and `request.data`.
- In v1, `onCall` receives `(data, context)` with `context.auth` and `data`.
- Authentication Guard: `if (!context || !context.auth) throw new HttpsError("unauthenticated", ...)`
  strictly enforces auth token presence. [Confirmed by source inspection]

C. HTTP Handlers:
- Signatures remain `(req, res)`.
- Explicit CORS preflight (`OPTIONS` -> 204) and headers (`Access-Control-Allow-*`)
  are added to ensure browser-based requests (from admin panels or web views)
  are not rejected.

D. verifyPayment Internal Cleanup Details:
- Previous State: In `iciciPaymentFunctions.js`, lines 356-450 contained internal
  `exports.reconcilePayments = onSchedule(...)` and `exports.activateSubscription = onDocumentUpdated(...)`
  declarations placed directly inside the async body of `verifyPayment`.
- Resolution: Removed these inner closures from inside `verifyPayment`.
- Impact on verifyPayment: Zero negative impact. The core payment status checking,
  mapping (`mapICICIStatus`), Firestore updating (`payments/{txnId}`), and tenant
  mirroring (`payment_transactions/{txnId}`) remain 100% intact. [Confirmed by source inspection]

16. REMAINING RISKS
================================================================================
1. Gen 2 to Gen 1 Function Replacement via Firebase CLI:
   - Technical Risk: Google Cloud treats Cloud Functions Gen 2 (Cloud Run backend)
     and Cloud Functions Gen 1 (Cloud Functions 1st gen backend) as distinct
     resource types.
   - When deploying a Gen 1 function with the exact same name as an existing Gen 2
     function, the Firebase CLI may report:
     "Cannot change function generation in-place".
   - Mitigation / Recommended Deployment Strategy:
     If Firebase CLI rejects the generation update, the existing v2 function
     must be deleted in Firebase Console or via CLI before deploying the v1
     replacement, OR deployed under a staged rollout.

2. Cloud Scheduler Job Overlap:
   - Technical Risk: Gen 2 schedulers use Cloud Run trigger jobs; Gen 1 schedulers
     use Cloud Pub/Sub topics + Cloud Scheduler.
   - Mitigation: When deploying Gen 1 schedulers, verify in Google Cloud Console
     (Cloud Scheduler tab) that orphaned Gen 2 scheduler jobs are removed to
     prevent duplicate daily reminder executions.
